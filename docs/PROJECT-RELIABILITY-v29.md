<a id="workflow"></a>
## Изолированный сценарий карточки

`scripts/verify-card-workflow.py` создаёт временную рабочую область, а результаты и квитанцию кладёт в явно заданный новый каталог. Источник — существующий обезличенный CIAN-снимок из тестов. Две фотографии намеренно синтетические. Во внешний источник скрипт не обращается.

Сценарий выполняет настоящий парсер и Node-генерацию, проверяет повтор исходного запроса без новой карточки, сохраняет отрицательное решение для вымышленного предмета и принимает безопасный рекламный черновик в тестовой карточке. Затем настоящий Chrome открывает Mac-редактор, сохраняет ручную правку, повторно открывает её, создаёт HTML, PNG, при запросе PDF и согласованный клиентский ZIP. Следующая правка делает прежние файлы устаревшими: они сохраняются, но не принимаются в новый комплект. Новый HTML открывается с телефонной оболочки, работающей в Chrome с экраном 393×852.

Отдельно проверяется экран версий: предпросмотр состава, явное скачивание диагностического ZIP, равенство версии живого процесса, файлов и вкладки, отсутствие URL, текста и приватного пути тестовой карточки в архиве. Квитанция содержит хеши созданных артефактов, реальные длительности и признаки выполненных этапов.

```bash
./.venv/bin/python scripts/verify-card-workflow.py \
  --workspace ~/.cache/redcn-verification/v29-card-flow-1 \
  --production-cache ~/.cache/redcn \
  --native-ai --pdf
```

Основной Python должен иметь уже установленный Playwright/Pillow и доступный Chrome. `--native-ai` использует существующий проверенный ARM/ONNX worker через рабочий `trained_photo_detector.analyze`; устанавливать ONNX Runtime в Python браузерного теста не требуется. Текст запускается существующим MLX-интерпретатором из конфигурации. `--candidate-adapter` позволяет явно проверить иной кандидат, не переключая рабочие настройки.

Настоящий вызов модели отмечается отдельно от качества. Если прямой текст не принят и сработал безопасный шаблон, квитанция явно содержит `fallback: true`. Синтетическая фотография подтверждает исполнение детектора и сохранение решения, но не его точность на квартирах. `fullCriterionMet` остаётся `false`: физический iPhone не подменяется изменённым User-Agent или размером окна.

<a id="soak"></a>
## Длительная смешанная нагрузка

Стенд состоит из `cli/project_soak.py`, `scripts/soak-project.py` и `scripts/soak-project-phase.py`. Исходники должны быть заморожены до начала прогона; квитанция фиксирует их контрольные суммы и проверяет отсутствие изменений. Реальную длительность измеряет монотонный таймер. Ни коэффициент ускорения времени, ни двухминутный preflight не могут дать `acceptance.twoHoursMeasured: true`.

Каждый цикл содержит четыре настоящие фазы: импорт локального снимка через parser/Node, работу Chrome с редактором, ONNX-инференс на синтетическом PNG и короткую разрешённую MLX-тренировку в отдельном каталоге. Каждая фаза даёт собственный результат; занятой ресурс, вытеснение рабочим запросом, общий deadline и ошибка различаются. Сборка стенда не выдаётся за испытание будущих изменений, которых в замороженном дереве ещё не было.

Используется общий `learning/model-resource.lock` рабочей установки. Если он занят обучением или анализом, фаза не захватывает ресурс силой. Появление пользовательского foreground-запроса завершает только принадлежащую стенду группу процессов. Сам сервер, чужой Chrome и рабочая модель не останавливаются. В отчёте имеются p50/p95, реальные задержки очереди, RSS принадлежащих процессов, ошибки, `vm_stat`/swap и версии. Вымышленное время не используется.

Физический сон всей рабочей машины этот скрипт не инициирует: он нарушил бы действующие сервер, обучение и удалённую связь. Без отдельной фактической проверки сна/пробуждения двухчасовой операционный результат остаётся частичным результатом RCN-356.

<a id="recovery"></a>
## Восстановление импорта и фотообработки

`cli/import_job_journal.py` сохраняет только хеш намерения, хешированный идентификатор запроса/актора, тип операции, этап, состояние, ID результирующей карточки и времена. Исходные URL, промпты и текст карточек не копируются в журнал. Файлы журнала приватные; количество записей ограничено. Записи идемпотентности не удаляются молча ради освобождения места.

Живое владение подтверждается файловой блокировкой `flock`, а не одним PID или строкой `running`. После гибели процесса ядро освобождает блокировку. При восстановлении запись получает `interrupted`; частичное сохранение не считается завершённым импортом и не запускается повторно само. Если карточка уже существует, предлагается открыть её и подготовить фото этой же карточки.

Повтор с тем же `requestId` и тем же намерением возвращает прежний job ID, включая после перезапуска сервера. Тот же идентификатор с изменённым намерением получает HTTP 409 `IMPORT_REQUEST_CONFLICT`. Телефон передаёт только исходное намерение импорта; смена профиля Mac между потерей ответа и повтором не создаёт ложное новое намерение. Actor определяется аутентифицированным сервером.

Mac UI хранит хеш параметров и случайный идентификатор до получения терминального результата. Phone UI сохраняет такой же минимальный pending-запрос в `sessionStorage`, чтобы повтор после потери ответа был безопасным. Сами URL и содержимое карточки в pending-запись не входят. После завершения, ошибки, отмены или восстановления UI останавливает ожидание и показывает доступную карточку. Поздний результат импорта не заменяет ручной текст, изменённый во время ожидания.

Обновление маркера `mediaStatus` после ошибки выполняется отдельной SQLite-транзакцией и не перезаписывает всю старую копию карточки. При завершении фотоанализа существующая защита сравнивает исходный текст/поля с текущими; несовпадающая ручная версия остаётся на месте.

Проверки включают реальный дочерний процесс с SIGTERM, параллельные одинаковые запросы, перезапуск локального HTTP-сервера, сохранение ручного китайского текста и телефонный повтор после изменения профиля. Это доказательства восстановления процесса и протокола. Они не называются проверкой физического сна Mac или сотовой сети iPhone.

<a id="source-drift"></a>
## Изменение схемы ЦИАН и Авито

`cli/source_schema_health.py` добавляет к разобранному источнику `sourceSchemaHealth`: покрытие цены, площади, планировки и описания; известные структурные маркеры; наличие JSON-LD; причины неполноты. Отсутствие числа остаётся неизвестным. Корректная студия не становится отсутствующей квартирой из-за нулевого числа отдельных комнат.

Состояния `recognized`, `partial`, `unsupported` отражают наблюдение структуры и результата разбора. Появление JSON-LD само по себе не доказывает полноту всех фактов: покрытие полей проверяется отдельно. Необычная схема получает предупреждение для оператора, а не выдуманные цену, запрет или количество техники.

Приватный видимый фрагмент ограничен 700 символами. Скрипты, стили, шаблоны и встроенные объекты не копируются; типичные URL, email, телефоны, аккаунты и обозначенные токены удаляются. Это вспомогательный приватный материал для проверки оператором, а не разрешение публиковать исходный текст. Клиентская проекция исключает весь `sourceSchemaHealth`; безопасная сводка содержит только фиксированные коды и булевы признаки. Диагностический ZIP не включает этот фрагмент.

Тесты используют два существующих обезличенных наблюдавшихся снимка v26 и искусственные изменения структуры. Для полного RCN-360 нужны дополнительные разрешённые снимки реальных новых форм, отдельные источники происхождения и измерение покрытия по этому расширенному набору.

<a id="client-bundle"></a>
## Согласованная ревизия клиентских материалов

Экспорт связан с подтверждением содержимого (`presentationReceipt`), полученным вместе с загруженной телефонной карточкой или ответом на сохранение Mac-карточки. Ревизия списка файлов не выдаёт такого подтверждения. Это закрывает воспроизведённую гонку: открытая карточка с ценой 80 000 ₽, последующая правка на Mac до 81 000 ₽, старый HTML вместе с новой ревизией списка — HTTP 409, без создания текущего материала. Старое подтверждение также нельзя приложить к новой ревизии. После явного «Обновить из карточки» телефон перечитывает содержимое с Mac и может создать согласованный материал.

Mac проверяет изменения редактора на всём ожидании сохранения, затем повторно проверяет тот же снимок после рендера. Сервер выдаёт подтверждение сохранения только для точного принятого payload; конкурентная правка до ответа возвращает 409. Чтение телефонной карточки проверяет ревизию после подбора фотографий. Подтверждение не попадает в клиентскую проекцию, ZIP или HTML. Этот контракт связывает штатный renderer с прочитанной карточкой; он не доказывает содержание произвольно подменённого HTML или пикселей PNG.

Регрессии: `test_client_bundle_consistency.py` — 9 проверок, включая точное воспроизведение старого HTML с новой ревизией и изменение во время PDF; `test_card_api.py` — 4 проверки, включая конкурентную запись между сохранением и HTTP-ответом; `presentation-export-boundary.test.mjs` — 6 асинхронных сценариев загрузки/сохранения/рендера.

После сборки 02.11.2026 выполнены настоящие браузерные сценарии в изолированном **Linux Chromium headless**: 3 теста `test_presentation_browser` (включая устаревший телефонный дизайнер, явную перезагрузку, первую запись новой карточки, HTML/PNG/PDF и скачивание с телефонной оболочки) и 5 тестов `test_phone_job_browser` (включая повтор после перезапуска и подготовку фото без дублирования карточки). Первый запуск дал 7 успешных сценариев и ошибку окружения PDF: дочерний процесс искал отсутствующий Google Chrome. Только этот сценарий повторён с `browser_channel='chromium'` в изолированной fixture; он прошёл за 9,149 с. Production-код не менялся для обхода ошибки среды. Итого все 8 сценариев прошли; это не результат macOS, Safari или физического iPhone. Нормальная проверка `validate-roadmap-evidence.py` после сборки также прошла по структуре и целостности ссылок, сохранив `acceptanceCompletenessOk=false` для ещё не подтверждённых приёмок.

Последующая сквозная проверка Mac обнаружила расхождение ревизий между форматами. Управляемая задержка реального UI photo-job воспроизвела его в Linux: HTML создавался до завершения анализа, а следующий экспорт сохранял новые `photoEdits.observations` и делал HTML устаревшим. Исправление ждёт завершения начальной загрузки, анализа и подбора кадрирования **до** экспортного сохранения; ожидание ограничено 30 секундами и отменяется при смене карточки. Оно не прерывает пользовательское AI-задание и не исключает метаданные из ревизии. Новый браузерный тест удерживает ответ анализа, проверяет отсутствие сохранений/экспортов до его завершения, затем получает HTML/PNG/PDF одной ревизии. Этот тест и первая запись новой карточки прошли за 7,147 с.

Сквозной сценарий `verify-card-workflow.py` сохраняет HMAC-диагностику карточки и media до/после каждого формата, не выводя значения полей. При ошибке его временная БД после остановки серверов сохраняется в приватном `workspace/private-fixture`; неудачный запуск не заменяется успешным задним числом. Полный сценарий в **Linux Chromium, без native AI** после исправления ожидания, заголовка версии и гидратации фото прошёл за 10,236 с: импорт, ручная правка и повторное открытие, три формата, согласованный ZIP, инвалидирование старых файлов, телефонное скачивание новой версии, явный диагностический ZIP и неизменность контрольных счётчиков. `passed=true`, `fullCriterionMet=false`, `nativeAIExecuted=false`; Mac и физический iPhone принимаются отдельно. Последующая узкая правка повторного анализа того же оригинала проверена отдельными тестами ниже; ей не приписывается повтор этого полного запуска.

`cli/client_bundle_consistency.py` связывает файл с сохранённой карточкой и идентичностями её исходных/обрезанных фото. Повторное сохранение точно тех же данных не меняет токен из-за одного времени в базе. Изменение текста, условий, фото или связанного crop делает материал устаревшим.

Токен — HMAC-SHA256 с отдельным приватным ключом рабочей области. Обычный публичный SHA от приватных полей мог бы помогать угадывать комиссию или внутреннюю заметку; HMAC этого свойства не имеет. Ключ не входит в клиентский комплект. После восстановления на другом рабочем месте старый файл не получает доверие новой ревизии автоматически.

`GET card-exports/<id>` возвращает актуальный `revisionSha256` только для отображения состояния файлов. `POST card-export` требует `expectedRevision` и `sourceReceipt`, которые дизайнер получил вместе с данными карточки. Отсутствие подтверждения или изменение карточки даёт HTTP 409 с предложением обновить карточку и пересоздать материал. Проверка выполняется до рендеринга, перед сохранением и после него, поэтому правка во время PDF не удостоверяет смешанную версию.

Существующие файлы отображаются как `current`, `stale` или `unverified`; байты устаревших файлов сохраняются. Их скачивание в качестве актуального комплекта и добавление в ZIP блокируются. `dossier-client` повторяет проверку после сборки ZIP; манифест фиксирует одну ревизию. Клиентский текст проходит существующую политику публикации, которая исключает комиссию и приватные данные.

Привязка версии не доказывает семантику произвольного растрового файла и не заменяет проверку фактов рекламной модели. Полнота RCN-361 по бесплатности услуг, технике, маршрутам и разнообразию зависит от профильных критериев ИИ.

<a id="photo-review-preservation"></a>
## Сохранение решений человека при загрузке и повторном анализе фото

Воспроизведены два независимых случая потери ручной проверки. В первом сохранённая карточка содержала анализ оригинала B, подтверждённый холодильник с количеством 1 и отклонённый диван; IndexedDB хранил старый bitmap A. Гидратация сначала подменяла анализ кешем A, затем очистка при получении настоящего неизменившегося B стирала оба решения. Во втором новый анализ того же B возвращал `candidates=[]`: карты `confirmed`/`rejected` оставались, но исчезали строки интерфейса и подтверждённое фото-доказательство, поскольку они строились только по новым предложениям модели.

Теперь сохранённые наблюдения карточки отделены от bitmap-кеша. Решение о применимости анализа принимается по фактическому canonical SHA сервера. Кеш может предоставить байты и производную только при совпадении оригинала; он не подменяет более свежую ручную проверку. При настоящей смене B → C решения B не переносятся на C. Перед экспортом обязательно выполняется новое чтение `photo/accepted`, даже если пятисекундный кеш отображения ещё действителен. Полученный ответ переиспользуется при подборе производной; уже загруженные байты с тем же SHA не скачиваются заново. `photo/load` остаётся запасным путём для ещё не загруженного оригинала и явного обновления.

Повторный анализ сначала подтверждает canonical SHA, а ответ модели обязан относиться к этому же оригиналу. Если из новых предложений исчезла ранее проверенная категория, сохраняется только её прежняя строка с явным `reviewOrigin=operator-kept` и `reviewOriginalId`. Подтверждение и количество либо отказ продолжают действовать; строка не считается новым результатом модели, автоматические флаги выключены. Интерфейс пишет «сохранено решение оператора для этого оригинала», а источник сохранённого фото-доказательства — `operator-kept`. Непроверенные догадки и решения другого оригинала не переносятся.

В `test_photo_cache_decisions_browser.py` выполнены четыре настоящих браузерных сценария на вымышленных изображениях и временных данных:

| Сценарий | Проверяемый результат |
| --- | --- |
| Старый IDB A, сохранённый анализ и фактический оригинал B | Обе ручные строки, галочки, количество и сохранение карточки остаются привязаны к B |
| Фактическая замена сохранённого B на C | Анализ и решения B не присваиваются C |
| Замена B на C менее чем через 5 секунд после экспортного чтения | Новое чтение canonical SHA, загрузка C; в полученном HTML проверяются пиксели C и отсутствие B |
| Новый анализ того же SHA без предложений | Подтверждённый холодильник и отклонённый диван сохраняются; непроверенная кровать исчезает, доказательство и ручной текст карточки сохраняются |

Все четыре сценария вместе с управляемой задержкой анализа перед экспортом прошли **5/5 за 12,144 с** в Linux Chromium. До исправления отдельный сценарий повторного анализа воспроизвёл потерю строки холодильника; это зафиксированная регрессия, а не проверка только нового кода. Дополнительно `photo-review-journal.test.mjs` и `photo-evidence.test.mjs` прошли **8/8**, включая запрет переноса на другой SHA и сохранение происхождения `operator-kept`. Эти результаты проверяют работу интерфейса и хранения; они не измеряют качество распознавания или физический iPhone.

<a id="versions-diagnostics"></a>
## Версии и приватный диагностический пакет

При сборке метка версии вставляется сразу после верхнего `<meta charset>` и проверяется на обеих оболочках. У desktop-шаблона нет явного `<head>`, поэтому прежняя вставка по этой строке пропускала верхнюю метку, несмотря на успешную сборку. Сквозной браузерный сценарий обнаружил это как `desktop-shell-unversioned`; после исправления он проверяет одинаковую версию сервера, страницы Mac и телефонной оболочки.

`scripts/build-release-identity.py` создаёт `data/build-identity.json`. Сборка включает идентификатор в обе оболочки. Сервер один раз фиксирует снимок исходников и Git при старте; диагностика отдельно вычисляет состояние файлов на диске. Поэтому пересборка без перезапуска старого сервера не делает старый процесс актуальным. UI различает изменённый код, несобранную оболочку, старую вкладку и необходимость перезапуска Mac-сервера.

Manifest — результат сборки с фактическим временем и коммитом, поэтому исключён из Git. Штатный `scripts/install-redcn.py` вызывает `scripts/build.mjs`, который создаёт manifest перед чтением: установочный ZIP не зависит от заранее отслеживаемого файла. После обновления исходников требуется сборка на новом HEAD и перезапуск сервера.

Экран показывает выбранный текстовый адаптер, хеш его весов, закреплённую фотомодель и версию словаря. Хеш доступного файла — идентичность, а не приёмка качества. Для базовой текстовой модели сообщается конфигурация, но полная проверка всех базовых весов не заявляется. Приватные пути, содержание словаря, токены и карточки не возвращаются.

API `release-diagnostics` доступен через существующую проверку владельца Mac. `status` только читает. `preview` возвращает перечень трёх JSON-файлов и их размеры. `download` требует точный `expectedPreview`: если состояние успело измениться, состав нужно обновить. ZIP дополнительно содержит `manifest.json` с контрольными суммами.

В пакет входят версии, агрегаты исходов и этапов импорта, фиксированные классы ошибок, сохранённые состояния очереди и ограниченная история кандидатов. Сохранённое `running` явно не выдаётся за доказательство живого процесса. Можно выбрать один запуск обучения по неприватному идентификатору. Произвольные тексты исключаются посредством allowlist, включая исходные исключения, промпты, URL, контакты, пути и содержимое модели обучения.

Предельный размер — 256000 байт. Архив собирается в памяти и скачивается только по нажатию; временных ZIP на диске и внешней отправки нет. Отдельные тесты проверяют приватные sentinel-строки, смену состава между preview/download, превышение лимита, выход за пределы каталога и символические ссылки.

<a id="roadmap-proof"></a>
## Проверка roadmap и доказательств

```bash
python3 scripts/validate-roadmap-evidence.py \
  --issue /path/to/saved-issue.json \
  --receipts /path/to/receipts.json \
  --ci-receipt /path/to/ci-result.json \
  --output /path/to/roadmap-audit.json
```

Проверка связывает ID, точный текст критерия, зависимости, локальные доказательства и коммит. Выявляются повтор ID, отсутствующий предшественник, цикл, удалённая задача при наличии предыдущего плана, отсутствующий файл/якорь и расходящиеся статусы ROADMAP, сайта и сохранённого GitHub issue.

Квитанция содержит `taskId`, `kind`, `origin`, `artifact`, `sha256`, `criterionSha256`, `commit`, `passed`, `coversAcceptance`. Для двухчасового запуска также требуется действительное `actualDurationSeconds`. Типы `unit-test`, `browser-emulation`, `native-runtime`, `physical-device`, `physical-sleep-wake`, `independent-review`, `data-evaluation` и `source-audit` различаются. Синтетические данные не подтверждают физическое устройство. Наличие плана не подтверждает исполнение.

Артефакт должен соответствовать хешу, критерий — своей версии, квитанция — проверяемому коммиту. Внешний registry квитанций можно формировать после коммита, чтобы не создавать самоссылку с хешем ещё не существующего коммита. Сохранённый результат CI сравнивается с этим же коммитом; инструмент честно отмечает, что удалённый статус не был им независимо запрошен. Авторизованный GitHub-процесс должен получить результат отдельно.

`structuralOk`, `proofIntegrityOk`, `acceptanceCompletenessOk` и проверка всех представлений отчётливо разделены. Обычный запуск допускает старую нетипизированную историю как явный пробел и падает при ошибках структуры/целостности. `--strict` дополнительно требует полноту доказательств, сравнение сайта/issue и совпадающую квитанцию CI. Режим не переписывает план и не увеличивает процент готовности.

Первичная сверка v28 нашла отсутствующие якоря v10/v11, ссылку на необязательный отсутствующий словарь и несовпадение несобранного `docs/plan.json`. Исправление таких ссылок требует реального существующего доказательства; создавать вымышленные отчёты ради зелёного результата нельзя.
