# Постоянный адрес TUNA: существующий сервис и защита от дублирования

На Mac уже зарегистрирован официальный пользовательский сервис TUNA **`redcn-phone`**. Чтение реестра установленным клиентом `tuna service list --json` подтвердило работающий PID 1445, существующий домен `free-quail-5273.a.tuna.free` и явный upstream `127.0.0.1:8767`. Создавать второй `app.redcn.tuna` для этого Mac не требуется. В этом проходе новый автозапуск не устанавливался.

Первоначальная проверка файлов по маске `*tuna*` пропустила `~/Library/LaunchAgents/redcn-phone.plist`. Отсутствие файла `app.redcn.tuna.plist` не означает отсутствие управляемого туннеля. Теперь проверка опирается на официальный реестр сервисов, а не на имя файла.

Актуальная [документация TUNA HTTP](https://tuna.am/docs/tunnels/http/) подтверждает один бесплатный постоянный поддомен на аккаунт. Существующий адрес не требует нового домена, регистрации или платной подписки. [Официальный менеджер сервисов](https://tuna.am/docs/tunnels/guides/service/) управляет текущим сервисом; повторять `service install` не нужно.

## Read-only проверка

```bash
python scripts/install-tuna-launchagent.py --check-existing-pid 1445
```

По умолчанию выполняется dry-run. Скрипт вызывает установленный TUNA только с `service list --json`, разбирает результат в памяти и выводит очищенную сводку. `Args`, `File`, `Log`, произвольные значения параметров и исходный JSON реестра не печатаются и не сохраняются. Файлы авторизации, конфигурация аккаунта, cookies, окружение и логи не читаются. Сам TUNA использует свою существующую авторизацию внутренним штатным способом.

Сводка подтверждает точные имя сервиса, пользовательскую область, PID, исполняемый файл, домен и телефонный loopback-upstream. Внутренний параметр `--service redcn-phone` разрешён при проверке процесса только при совпадении имени и PID с проверенной записью реестра. Одного имени в аргументах процесса недостаточно. Порт редактора `8765` не принимается.

## Защита от конкурирующего LaunchAgent

`scripts/install-tuna-launchagent.py` сохраняется как защитная утилита и вариант подготовки для чистого Mac:

- Совпадающий официальный `redcn-phone` → `already-managed`, без нового plist, каталога или команды запуска; `--install` также ничего не создаёт.
- Реестр недоступен, повреждён, содержит неизвестные или несовпадающие регистрации → установка запрещена.
- Только успешно прочитанный **пустой** реестр допускает создание нового fallback-plist с отдельным явным `--install`. Существующий plist никогда не читается, не заменяется и не перезаписывается при гонке создания.

Для чистой установки подготовленные литеральные аргументы ограничены следующим набором:

```text
/opt/homebrew/bin/tuna
http
127.0.0.1:8767
--domain=free-quail-5273.a.tuna.free
--inspect=false
--https-redirect
--log=stdout
```

Это запасной план, а не описание нового изменения текущего сервиса. Shell не используется; инспектор запросов выключен, включено HTTPS-перенаправление. `--log=stdout` отключает TUI согласно [документации TUI](https://tuna.am/docs/tunnels/tui/); план перенаправляет stdin/stdout/stderr в `/dev/null`.

Fallback-plist содержит `RunAtLoad=true`, `KeepAlive=true`, `ThrottleInterval=30`, `Umask=077`. Новые каталоги получают `0700`, новый файл `0600`; права существующих общих каталогов не меняются. Подготовленный plist на macOS проверяется `plutil -lint -` через stdin. Утилита не выполняет `launchctl`, `service restart`, остановку процесса, вход или изменение тарифа.

## Что подтверждено для текущего Mac

Очищенные метаданные, полученные оператором read-only, сохранены в [tuna-existing-service-20261101.json](benchmarks/tuna-existing-service-20261101.json). У существующего `redcn-phone.plist` подтверждены `RunAtLoad=true`, `KeepAlive=true` и права `0600`. Время создания/изменения plist предшествует времени текущей загрузки macOS; работающий сервис наблюдался после этой загрузки. Это доказательство существующего сервиса после реальной загрузки, а не результат установки нового агента в этом проходе. Причина инициации конкретного запуска процесса отдельно не утверждается.

Согласно [документации Apple launchd](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/CreatingLaunchdJobs.html), `~/Library/LaunchAgents` относится к пользовательской сессии. Это не обещает доступность до входа в macOS.

Любая дальнейшая штатная операция с существующим сервисом остаётся отдельным операторским действием после проверки здоровья сервера v25, `activeJobs=0` и отсутствия активных попыток диагностической кампании. В этом проходе сервис и сервер не перезапускались, PID не завершался, Mac не перезагружался.
